BitDistill 4-Stage Miniaturization Plan

Kimi K2.5 → 1.58-bit Dense Student via BitNet Distillation

Objective: Prove the BitDistill pipeline (Wu et al., arXiv:2510.13998) at progressively larger scales, culminating in a 1.58-bit dense student distilled from Kimi K2.5 (1T parameter MoE teacher).

Method: BitDistill — a three-stage QAT framework combining SubLN architectural refinement, continual pre-training, and MiniLM-style multi-head attention + logits distillation.

End state: A 32–70B dense model with ternary {-1, 0, +1} weights, ~10× memory reduction, ~2.65× CPU inference speedup, running on a single high-end consumer GPU.

Foundational Concepts

Before any stage begins, the team must have a shared working understanding of the following. These are not tasks to complete — they are the conceptual substrate every engineering decision rests on.

1.58-bit Quantization

Every weight in the model is mapped to one of three values: -1, 0, or +1. This is achieved via per-tensor quantization using the absmean function:

Q_w(W) = Δ · RoundClip(W / (Δ + ε), -1, 1)
where Δ = mean(|W|)

Activations are kept at INT8 using per-token absmax quantization. Because RoundClip is non-differentiable, gradients during training are approximated using the Straight-Through Estimator (STE): the gradient flows as if the quantization step didn't exist. This is a known approximation with known failure modes — the team should read the original BitNet b1.58 paper before starting.

SubLN (Sub-Layer Normalization)

The core architectural modification. In standard transformers, LayerNorm is applied only at block input (pre-norm). SubLN inserts additional RMSNorm layers at two positions inside each transformer block:

  1. Before the output projection of the Multi-Head Self-Attention (MHSA) block
  2. Before the output projection of the Feed-Forward Network (FFN) — specifically before W_down in a SwiGLU FFN

The rationale: 1.58-bit quantization causes activation variance to explode at projection layers. SubLN variance-stabilizes the hidden states before they enter quantized linear operations. Without it, training is unstable and performance degrades predictably with model size.

The Three BitDistill Training Stages

These map to the paper's Stage 1 / Stage 2 / Stage 3 and must be executed in this exact order:

  • Stage A — Modeling Refinement: Insert SubLN. Convert all linear weights to 1.58-bit representation. This produces an architecturally modified model that is immediately inferior — that's expected.
  • Stage B — Continual Pre-Training (CT): Train the modified model on a small general corpus (~10B tokens) using only standard language modeling loss. This reshapes the weight distribution from the initial near-Gaussian (FP16 inherited) toward the bimodal near-boundary distribution characteristic of models trained from scratch with ternary weights. This distribution shift is what makes downstream fine-tuning stable and scalable.
  • Stage C — Distillation Fine-Tuning: With the FP16 model as teacher and the CT-warmed student, apply combined logits distillation (KL divergence on softened outputs) + multi-head attention relation distillation (from MiniLM) + cross-entropy on the task data. The total loss is: L = L_CE + λ·L_LD + γ·L_AD

Why the Staging Ladder Exists

The paper only validates BitDistill up to 4B parameters. Every stage in this plan answers a specific open question:

Stage Open Question Being Answered
Stage 0 Does our codebase correctly implement SubLN, STE, and the three-loss distillation?
Stage 1 Does BitDistill hold at 32B? Does 10B CT tokens converge weight distribution at this scale?
Stage 2 Does 10B CT tokens remain sufficient at 72B, or do we need 20–30B?
Stage 3 How do we bridge the MoE-to-dense knowledge gap when the teacher is an MoE model?

Stage 0: Sanity Check

Teacher: Qwen3-8B (FP16) → Student: 1.58-bit Qwen3-8B Duration: 2–3 weeks | Team: 2–3 people | Compute budget: ~USD 3,000–USD 6,000

Goal

This stage produces zero scientific value. It exists entirely to validate that your engineering stack is correct before spending real money. The questions you are answering are: Did I implement SubLN correctly? Does STE gradient flow work in my framework? Do the three loss functions produce meaningful gradients? Does the training loop run for 10B tokens without crashing?

Preparation

Environment setup: Configure a GPU training environment with PyTorch + HuggingFace Transformers. The team must decide and commit to a distributed training framework — either DeepSpeed ZeRO-2/3 or PyTorch FSDP. Both work; pick one and standardize. Set up experiment tracking (Weights & Biases or equivalent) from day one.

Model acquisition: Download Qwen3-8B weights from HuggingFace. Verify the model can do a clean forward pass in FP16 before touching anything.

Dataset preparation: Download the FALCON RefinedWeb corpus subset (~10B tokens). Write a tokenization and data loading pipeline that produces batches of 512-token sequences. Verify no data leakage between CT and fine-tuning splits.

Baseline establishment: Fine-tune the unmodified FP16 Qwen3-8B on your chosen downstream task(s) using standard SFT. Record all benchmark numbers. This is your performance ceiling — every downstream number in this stage will be compared to it.

Stage A: SubLN Architectural Modification

This is a model surgery task, not a training task. The deliverable is a modified version of Qwen3-8B's architecture with SubLN layers inserted.

What needs to be written: A model patching script that loads the original Qwen3-8B config and weight file, adds two new RMSNorm modules per transformer layer (one after MHSA concatenation, one after FFN gating), and saves the modified model. The original linear weights are then quantized in-place using the absmean function. The resulting checkpoint is larger in terms of python objects (new norm parameters) but the linear weights are now in INT format.

Verification: After modification, run a forward pass. Check that output logits are in a reasonable range (not NaN, not exploding). Check that the new SubLN modules have non-trivial scale parameters (they should initialize to 1.0 and not immediately die). Check that weight quantization produced the expected {-1, 0, +1} distribution by sampling 100 weight tensors and plotting their histograms.

What correct SubLN insertion looks like: In the MHSA block, the computation order changes from Y = X + Attention(X) @ W_out to Y = X + SubLN(Attention(X)) @ W_out. In the FFN block (SwiGLU), the computation changes from X_next = Y + (Y @ W_up ⊙ σ(Y @ W_gate)) @ W_down to X_next = Y + SubLN((Y @ W_up ⊙ σ(Y @ W_gate))) @ W_down. This needs to be reflected in the model's forward pass code, not just the weight file.

Stage B: Continual Pre-Training

Train the SubLN-modified, 1.58-bit quantized Qwen3-8B on ~10B tokens of FALCON corpus using standard causal language modeling loss. No task data. No teacher.

Training configuration to determine: Learning rate (start with 1e-4, with warmup over first 500M tokens then cosine decay), batch size (effective ~1M tokens/step), max sequence length 512–2048, gradient clipping at 1.0. All decisions should be logged.

What to monitor: Training loss curve — it should descend smoothly and not spike. Weight distribution at checkpoints — at the end of Stage B, weight histograms should show the characteristic bimodal shape (mass concentrated near the -1/0 and 0/+1 transition boundaries) that Figure 2 in the BitDistill paper demonstrates. If they still look Gaussian, CT did not converge. Either train more tokens or reduce the learning rate.

Checkpoint frequency: Save every 500M tokens. These checkpoints are your diagnostic trail.

Stage C: Distillation Fine-Tuning

Fine-tune the CT-warmed student using the three-loss objective, with the FP16 Qwen3-8B as teacher.

What needs to be written: A training loop that runs both teacher and student in the same process (teacher in eval mode, student in train mode), computes the three losses, and backpropagates only through the student. Memory management is the key engineering challenge here — at 8B, the teacher requires ~16GB FP16 and the student ~2GB 1.58-bit, so this fits on a single A100.

Loss function implementation: Three components:

  • L_CE: Standard cross-entropy between student predictions and ground truth labels
  • L_LD: KL divergence between softened teacher logit distribution and softened student logit distribution. Temperature τ = 5.0. Both distributions are softmax(logits/τ).
  • L_AD: Multi-head attention relation distillation at a single selected layer (not all layers). For the Q, K, and V projections at that layer, compute the self-relation matrix (QQ^T, KK^T, VV^T) for both teacher and student separately, apply softmax, and compute KL divergence. Apply to the final 20% of layers by default (layers 6–8 of 9 for 8B). Run a sweep over layer indices during Stage 0 — the paper finds later layers consistently outperform earlier ones, but the exact optimum varies by model.

Coefficient tuning: The paper uses λ=10, γ=1e5 for classification and λ=1, γ=1e3 for summarization. These are not universal. For Stage 0, run 4–6 short coefficient sweeps on a 100M-token mini-run before the full distillation. Log L_CE, L_LD, and L_AD separately and verify no single loss dominates to zero.

Stage 0 Exit Criteria

Before moving to Stage 1, all of the following must be true:

  • Training completes 10B CT tokens without NaN/divergence
  • Weight histograms post-CT show bimodal near-boundary distribution
  • Distillation fine-tuning runs without errors across at least one full epoch
  • Student achieves >90% of FP16 teacher performance on the chosen benchmark
  • Inference runs correctly in bitnet.cpp or equivalent 1.58-bit runtime
  • All code is version-controlled, all experiments are logged, all checkpoints are saved

Stage 1: True Proof of Concept

Teacher: Qwen3-32B (FP16) → Student: 1.58-bit Qwen3-32B Duration: 6–10 weeks | Team: 4–6 people | Compute budget: ~USD 30,000–USD 60,000

Goal

This is the stage with genuine scientific value. Qwen3-32B is the largest pure standard transformer in the Qwen3 dense family — the same architectural family as the models the BitDistill paper tested. Passing this stage with strong results gives you a legitimately publishable result: BitDistill confirmed to scale to 32B parameters.

The primary scientific question is: does the 10B continual pre-training token budget that the paper used for ≤4B models converge the weight distribution at 32B? If not, what is the right budget?

Preparation

Compute planning: At 32B parameters, a single training run of 10B CT tokens requires roughly 8–16× H100s for a reasonable wall-clock time (2–3 weeks). You must have a cloud compute contract or reserved GPU capacity before starting. Plan for at least 2 full training runs plus ablation capacity.

Scaled data pipeline: The tokenization pipeline from Stage 0 must now handle parallel data loading across multiple nodes. Verify your data loader saturates GPU compute — a common bottleneck at this scale.

Teacher availability: The FP16 Qwen3-32B teacher must be available for inference during Stage C. At 32B FP16, this requires ~65GB VRAM. Teacher and student will run simultaneously during distillation — plan your memory budget accordingly. With 4× H100 (320GB total), teacher runs on 1–2 GPUs, student on the remaining.

New Engineering Work in Stage 1

Distributed training correctness: The SubLN insertion, STE gradient flow, and three-loss distillation must all work correctly under tensor parallelism and/or FSDP. This requires explicit verification — bugs in gradient synchronization across ranks are silent and produce subtly wrong training dynamics.

Attention distillation under tensor parallelism: When attention heads are split across GPUs, computing the cross-model self-relation matrix (teacher vs student) requires gathering head outputs. Write a utility that correctly gathers and aligns attention states across ranks before computing L_AD. Test this on a 2-GPU run before scaling to 8+.

Memory-efficient teacher inference: The teacher runs in eval mode with no gradient storage. Use torch.no_grad() and optionally FP8 precision for teacher inference to halve its memory footprint. The teacher's intermediate activations (hidden states at the distillation layer) must be captured and passed to the student loss computation — implement this as a forward hook rather than modifying the teacher's forward pass.

Checkpoint sharding: At 32B, model checkpoints are 60–130GB depending on precision. Implement sharded checkpoint saving and loading. Verify that resuming from a checkpoint produces identical training dynamics to a run that never interrupted.

Stage B at 32B Scale: The Key Diagnostic

The most important thing to measure during Stage B (CT) at 32B is whether 10B tokens is enough. Do this by saving checkpoints at 2B, 5B, 7B, and 10B tokens, then running Stage C (distillation fine-tuning) from each checkpoint on a short benchmark task. Plot performance vs CT tokens consumed. Look for the point of diminishing returns. If performance is still improving significantly at 10B tokens, you need to extend to 15B or 20B. This diagnostic run is not optional — it provides the data that Stage 2 planning depends on.

Stage C: Distillation at 32B

The same three-loss framework as Stage 0, now at 32B scale.

Key difference: The optimal distillation layer index from Stage 0 may not transfer. At 32B (64 layers vs 36 for 8B), the "final 20% of layers" heuristic points to layers 52–64. Run a compressed 5-layer sweep before the full distillation run to confirm.

Coefficient behavior at scale: The paper shows λ and γ do not need to scale with model size — they are task-dependent, not size-dependent. Use Stage 0 values as starting point and verify loss component balance in the first 1000 steps before committing to a full run.

Performance Expectations

Based on the paper's scaling behavior:

  • Classification tasks (MNLI, QNLI, SST-2): expect 98–100% of FP16 performance
  • Summarization (CNNDM ROUGE scores): expect 97–99% of FP16 performance
  • Hard reasoning benchmarks: expect 90–95% of FP16 performance

If performance is below these ranges and the paper's benchmarks hold, the most likely culprits in order of probability: insufficient CT tokens, incorrect SubLN insertion, miscalibrated loss coefficients, and distributed training gradient errors.

Stage 1 Exit Criteria

  • CT weight distribution convergence confirmed at 10B tokens (or documented that more tokens are needed)
  • Student achieves ≥95% of FP16 teacher performance on at least two standard benchmarks
  • Distillation layer sweep completed and optimal layer documented
  • Inference validated on CPU with bitnet.cpp, throughput and memory numbers recorded
  • Ablation table documenting effect of each stage (A, B, C) individually
  • Results are publication-quality — write them up in a 2–4 page technical report

Stage 2: Scale Validation

Teacher: Qwen2.5-72B (FP16) → Student: 1.58-bit Qwen2.5-72B Duration: 12–16 weeks | Team: 8–11 people | Compute budget: ~USD 100,000–USD 150,000

Goal

Validate that the BitDistill pipeline scales to 72B dense parameters. The primary unknowns at this scale are: (1) whether the CT token budget needs to increase beyond 10B, and (2) whether the simultaneous teacher+student VRAM footprint creates engineering constraints that require architectural solutions.

Qwen2.5-72B is chosen because it is the largest open-source dense Qwen model (80 layers, 72.7B params, GQA with 64 Q / 8 KV heads, 128K context, trained on 18T tokens), has the same GQA + SwiGLU + RMSNorm + RoPE architecture as the Qwen3 family, and is fully open-weight under Apache 2.0.

New Engineering Challenges at 72B

Memory budget for teacher+student co-training: The FP16 teacher is ~145GB. The 1.58-bit student is ~14–18GB of weights, but during training, gradient and optimizer states push effective memory to ~100–140GB. Combined, you need ~280–320GB of GPU memory. A 4× H100 node (320GB) is exactly sufficient. Plan training to use teacher on 2 GPUs in inference mode, student on all 4 GPUs in training mode with FSDP. Any memory budget overrun will OOM silently or cause crashes.

SubLN at 80 layers: Stage 0 and 1 SubLN insertion was at 36 and 64 layers respectively. At 80 layers and hidden size 8192, each SubLN module has 8192 learnable scale parameters. Total new parameters from SubLN: 80 × 2 × 8192 = ~1.3M. Negligible vs 72B total but must be initialized correctly (scale=1.0, no bias in RMSNorm).

GQA-aware attention distillation: Qwen2.5-72B uses GQA with 64 Q heads and 8 KV heads. The attention relation matrix computation in Stage C must handle this correctly — do not naively compute QQ^T with the 8-head KV tensors expanded to 64 heads without verifying this is mathematically sound. The paper's implementation computed relations on the raw Q, K, V projections before any head expansion. Verify this against the paper's algorithm pseudocode (Algorithm 1).

Gradient checkpointing: At 72B with long sequences, intermediate activations alone can exhaust memory. Enable activation checkpointing (recompute on backward pass) on all transformer layers. This halves memory at the cost of ~30% more compute. It is necessary, not optional.

CT Token Budget Determination

The most important deliverable of Stage 2 is a definitive answer to the CT token budget question at 72B scale.

Proposed approach: Run CT at 72B to 30B tokens total, saving checkpoints every 5B tokens. At each checkpoint, run a fast 500M-token distillation fine-tune on a benchmark task. Plot performance as a function of CT tokens. The knee of the curve is your required budget. Budget for this diagnostic to cost 40–50% of the total Stage 2 compute allocation.

If the knee is at 10B tokens: You can apply the same budget to Stage 3 (Kimi K2.5). If the knee is at 20–25B tokens: Stage 3 planning needs to be revised upward accordingly.

Stage C Specifics at 72B

The key implementation question is whether to use a single-GPU teacher or a sharded teacher for distillation. Options:

Option A — FP8 teacher on 2 GPUs (recommended): Convert teacher weights to FP8 before distillation. FP8 at 72B occupies ~72GB — fits on 2× H100s with some KV cache headroom. This keeps teacher inference fast and reduces memory pressure on student training GPUs. Risk: FP8 teacher accuracy must be verified to be within 0.5% of BF16 teacher on the distillation task before committing.

Option B — Full BF16 teacher on 4 GPUs, student on 4 GPUs using an 8-GPU node: Simpler memory model, but requires an 8× H100 node (~USD 25–30/hr on cloud). Appropriate if FP8 conversion introduces noticeable accuracy drop.

Inference Validation

At the conclusion of Stage 2, run the 1.58-bit student through the bitnet.cpp inference engine (or equivalent ternary-weight-optimized runtime) on CPU. Measure:

  • Tokens per second on 32-core CPU
  • Peak RAM usage
  • Comparison to FP16 inference speed and memory

These numbers are the business case for the entire project. They should be ~2.65× faster and ~10× more memory-efficient than FP16 — consistent with the paper's claims at smaller scales.

Stage 2 Exit Criteria

  • CT token budget for 72B documented with empirical convergence curve
  • Student achieves ≥95% of FP16 teacher on classification and ≥97% on summarization
  • GQA attention distillation correctness verified against expected behavior
  • FP8 teacher accuracy impact measured and documented
  • CPU inference numbers measured (tok/s, RAM) and compared to FP16 baseline
  • Technical report updated with 72B results

Stage 3: The Real Target

Teacher: Kimi K2.5 (1T MoE, 32B active) → Student: 1.58-bit Dense 32B–70B Duration: 20–30 weeks | Team: 15–20 people | Compute budget: ~USD 1.5M–USD 3.5M

Goal

Produce a 1.58-bit dense model that distills the knowledge of Kimi K2.5 — a 1-trillion parameter MoE model with 384 experts, 32B active parameters per token, 15T token training, native multimodal capabilities, and state-of-the-art agentic performance. The student is a dense 32–70B model with ternary weights, deployable on 1–2 consumer GPUs.

The Fundamental New Challenge: MoE-to-Dense Distillation

Everything up to Stage 2 was dense teacher → dense student. Stage 3 introduces a qualitatively different problem: the teacher activates only 8 of its 384 experts per token. Different input sequences route to different experts. Any single forward pass through the teacher captures only ~2% of its total parameter knowledge. The student, being dense, must learn to represent all 384 experts' knowledge in its unified parameter space.

This is not a solved problem at this scale. The known challenge: if you train the student only on data distributions that consistently route to the same few experts, the student learns only those experts' behaviors. You need to ensure sufficient expert coverage during the CT and distillation phases.

Teacher Infrastructure

Running Kimi K2.5 inference at scale for distillation data generation is the largest single engineering challenge of the project.

What needs to be built: A teacher inference pipeline capable of generating and caching soft logits (probability distributions over the vocabulary) + intermediate hidden states (at the distillation layer) for a large corpus. This pipeline must:

  • Run Kimi K2.5 in distributed mode across at least 16× H100s (model requires ~600GB at FP16, fits on 8× H100s with tensor parallelism but needs headroom)
  • Cache output logits (top-K=1000 tokens sufficient, not full 164K vocab) to disk in a compressed format
  • Cache hidden states at the selected distillation layer
  • Process tokens at roughly 2,000–3,000 tok/s sustained throughput
  • Be fault-tolerant (teacher inference should resume from checkpoint, not restart)

Storage requirement: Top-1000 logits per token × 32-bit float × 10B tokens = ~40TB. This is a significant infrastructure cost. Use FP16 logit storage to halve this to ~20TB.

Alternative approach — online distillation: Rather than pre-caching, run teacher inference online during student training. This doubles the per-step compute cost but eliminates the storage requirement. At 32B active teacher parameters, online inference adds roughly 40–60% overhead to the training step. Evaluate against cached approach based on your compute/storage cost ratio.

Expert Coverage Strategy

To ensure the student learns from all 384 experts, the training corpus must be carefully constructed to maximize routing diversity.

What needs to be assembled: A curriculum dataset that includes highly diverse content types: mathematical proofs, source code in 30+ programming languages, scientific literature, creative writing, multilingual documents (Kimi K2.5 supports 164K vocab including many non-Latin scripts), structured data (tables, JSON, code with comments), and multi-turn conversation. The hypothesis is that expert routing correlates with content domain — different experts specialize in different modalities and subjects. A diverse curriculum forces the teacher to route through most of its expert space.

Diagnostic: After caching teacher outputs on the curriculum, analyze routing statistics. Compute, for each of the 384 experts, what fraction of the cached tokens activated that expert. If any expert has <0.1% activation rate, that domain is underrepresented in the curriculum and the student will not learn it. Expand the curriculum in those domains.

Student Architecture Decision

The student is a new dense model, not a modified version of any existing model. You must choose its architecture.

Option A — Qwen3-32B architecture as student: This is the lowest-risk option. The architecture is identical to Stage 1's student. SubLN insertion is already validated at this scale. Fine-tuning recipes, evaluation harnesses, and inference code all transfer directly.

Option B — 70B dense student: Larger capacity = better knowledge absorption from the 1T teacher. But validation at 70B requires extending Stage 2's work, and the simultaneous teacher (Kimi K2.5 at ~600GB FP16) + student (70B in training mode at ~140GB BF16 + optimizer states) VRAM budget requires a 16× H100 node. More expensive and higher risk.

Recommended start: Begin with Qwen3-32B architecture student. If performance ceiling is unsatisfactory after Stage 3 first run, extend to 70B for a second run.

Vision and Multimodality Handling

Kimi K2.5 is a native multimodal model with a 200M parameter MoonViT3d vision encoder. For Stage 3, a pragmatic decision must be made:

Approach A — Text-only student: The student is a text-only LLM. Distillation uses only text tokens. The teacher's MoonViT3d encoder is not used. The student inherits K2.5's text-domain reasoning and coding intelligence but not its vision capabilities. This is 80–90% of K2.5's value and 50% of the complexity.

Approach B — Multimodal student: The student includes a lightweight vision encoder (e.g., a frozen CLIP ViT-L or a distilled version of MoonViT3d). Distillation includes image-text pairs and video-text pairs. Far more complex but produces a genuinely multimodal output. Recommended only for Stage 3 iteration 2, after text-only distillation is working.

Recommendation: Start with Approach A. Deliver a text-only 1.58-bit student first. Multimodal extension is a follow-on research project.

Stage C at MoE Scale

The three-loss distillation framework is architecturally unchanged. The implementation difference is the teacher's MoE routing.

MoE expert output aggregation for attention distillation: In Kimi K2.5, each MoE layer's output is a weighted sum of the 8 active expert outputs. For attention distillation, the "teacher hidden state" at the distillation layer is the post-MoE-aggregation representation. This is well-defined and can be captured with a forward hook — no special MoE-specific distillation logic is needed at the activation level.

Logits distillation is unchanged: The teacher's output logits are the final LM head predictions — fully dense, regardless of internal MoE structure. Standard KL divergence applies.

Performance Expectations

Based on Stage 1–2 validated performance + published BitDistill claims:

Task Category Expected Student Performance vs Kimi K2.5
Text generation / instruction following 90–95%
Code generation (HumanEval, SWE-bench) 80–90%
Mathematical reasoning (AIME, MATH) 75–85%
Hard reasoning (GPQA Diamond) 70–80%
Multilingual tasks 85–92%

The gap vs a direct dense-to-dense distillation of similar scale is primarily due to the MoE-to-dense compression. These estimates will narrow if the curriculum coverage strategy successfully activates all 384 experts during training.

Stage 3 Exit Criteria

  • Teacher inference pipeline sustains >2,000 tok/s for 10B+ tokens without failure
  • Expert routing diversity verified — all 384 experts activated in curriculum
  • CT weight distribution convergence confirmed (same methodology as Stages 1–2)
  • Student achieves ≥80% of Kimi K2.5 on HumanEval and ≥75% on GPQA Diamond
  • CPU inference confirmed: memory ≤20GB, throughput ≥100 tok/s on 32-core CPU
  • Model weights released or prepared for release
  • Full technical report written documenting the MoE-to-dense distillation methodology

Cross-Stage Infrastructure

Evaluation Harness

Build this once in Stage 0 and maintain it through all stages. Should support: MMLU, GPQA Diamond, HumanEval, MATH, GSM8K, SWE-bench (proxy), CNNDM (ROUGE), MNLI/QNLI/SST-2. Must run identically against FP16 and 1.58-bit models. Output format: structured JSON with all scores, allowing direct stage-to-stage comparison.

Experiment Registry

Every training run should be logged with: commit hash, hyperparameter config, CT token count at distillation start, hardware used, wall-clock time, peak memory, and final benchmark scores. This registry is critical for debugging regressions and communicating results.

1.58-bit Inference Runtime

The project's output is only as valuable as the inference experience. From Stage 0 onward, verify that every student checkpoint runs correctly in a ternary-weight-optimized inference engine (bitnet.cpp is the current reference implementation). Do not allow a situation where training and inference codebases diverge.
